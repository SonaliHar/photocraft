## What landed

New crate `crates/ai-client` (package `photocraft-ai-client`, L6, native only), registered in `xtask/src/layers.rs`. It implements
`photocraft_engine::ai::AiProvider` exactly to SPEC amendment 11, with no HTTP dependency (HTTP/1.1 framing over `std::net::TcpStream`).

- `crates/ai-client/src/endpoint.rs`: `endpoint.json` (version 1, `127.0.0.1`, port, bearer token) from the platform path in amendment 11,
  or `CRAFT_AI_ENDPOINT`. Missing / unreadable / bad JSON / wrong version / port 0 / bad token -> `AiError::NoProvider`; a host other than
  `127.0.0.1` and a file over 64 KiB are reported as errors. `Debug` redacts the token.
- `crates/ai-client/src/http.rs`: request line + `Authorization`, `Host`, `Connection: close`, `Content-Length`; strict reply framing
  (rejects chunked, duplicate or non-numeric `Content-Length`, missing length on a body-bearing reply, non-UTF-8 headers, over-cap and
  truncated bodies). Connect timeout 2 s, read/write 30 s, JSON cap 64 KiB, per-call PNG cap. 204/304 with no length is an empty body.
- `crates/ai-client/src/pixels.rs`: `image` PNG (RGB/RGBA, 8-bit for U8 and 16-bit otherwise, f32 clamped 0-1 and rounded, big-endian
  samples) and `mask` PNG (8-bit gray); `result.png` back to f32 only when size, channels and depth match the request. Caps are checked
  before allocating; a non-finite sample is refused rather than sent.
- `crates/ai-client/src/protocol.rs`: the `job` JSON with the amendment's nine keys in the amendment's order, the multipart body
  (`job`, `image`, `mask` in that order, boundary chosen so the parts cannot contain it), job-id validation before it reaches a URL,
  state / provenance / task-list parsing, and the `{"error": "<sentence>"}` mapping.
- `crates/ai-client/src/provider.rs`: `CaimProvider` re-reads the endpoint file on every `submit` and stores that endpoint with the job,
  so `poll`, `result` and `cancel` go to the manager that took the job even after the file changes. 401 -> the token-mismatch sentence;
  other non-2xx -> the manager's sentence. At most 16 jobs are tracked, evicting the oldest.

## Known gaps and follow-ups

- **No `GET /v1/health` call.** The prompt says health is not required and `submit` reports a closed port as `NoProvider`; a health probe
  would only add a round trip. PC-04 may want one to decide whether to grey anything out.
- **No overall time limit on a job** (PC-01 review follow-up 2): each request has the protocol's 2 s connect / 30 s read timeouts, but a
  manager that keeps answering `running` keeps the job alive. The engine's poll loop owns that; if a cap is wanted it belongs there.
- **`CRAFT_AI_ENDPOINT` is read once, at construction** (`CaimProvider::new`); the file named by it is re-read per submit. PC-04 injects
  the provider at startup, which is the same lifetime, so this is fine - but a test that sets the variable after startup would not see it.
- **B04, B08, B12 in `agents/FEATURES.md` are not ticked**: each still needs the app side (PC-04) or a real manager (PC-06).
- **PC-04** injects `CaimProvider` into `apps/photocraft` and `apps/photocraft-cli` and returns provenance in the command result;
  **PC-05** adds the MCP automation test; **PC-06** runs this client against the real manager on the 4090.

## Review (Claude, Oct 13, 2026)

**Approved.** Read `Cargo.toml`, `lib.rs`, `endpoint.rs`, `http.rs`, the size caps in `provider.rs` and the conversions in `pixels.rs` against SPEC amendment 11 and AGENTS.md.

- No new dependencies beyond `png 0.18` (already in the tree); crate-level `forbid(unsafe_code)` and the no-panic deny list; registered at L6; the fake server is test-only.
- `endpoint.rs`: unusable file → `NoProvider`; a host other than 127.0.0.1 is refused; the token must be printable ASCII (no header injection) and is redacted from `Debug`; the file read is capped at 64 KiB even if its metadata lies.
- `http.rs`: strict framing as specified (no chunked, single numeric `Content-Length`, capped line and header sizes, UTF-8 headers, 204 without a body), timeouts set before writing, and every failure is a plain sentence.
- `provider.rs`: endpoint re-read per `submit` and kept with the job, so `poll`, `result` and `cancel` reach the manager that took it; the `result.png` cap comes from the request's size; the job table is bounded (16) and survives lock poisoning.
- `pixels.rs`: clamp, scale and round as specified; NaN encodes as 0 without panicking (and requests are validated upstream); PNG decoding runs under a byte limit sized to the expected image.

**Notes, not blocking:** the 16-job table evicts the oldest entry; with one job at a time that's fine, but CAIM-side queues in S2 may want it larger. Health checks (`GET /v1/health`) can come with U09 (status in Preferences).
